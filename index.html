FMCS Robot Experiment Audit

Two questions came up while reproducing the robot-arm experiments of Section VI-D. First, the oc_fmcs branch of the 3D experiments calls a hand-written phase controller rather than a learned flow-matching velocity field. Second, the Diffusion baseline scores 0% on every task, and in simulation the arm keeps jittering without reaching the target. This page answers both and reports results with an upgraded baseline.

Summary

Question 1

The observation is correct. In the robot experiments oc_fmcs is a hand-written finite-state machine that drives differential IK. No velocity field is learned, and every learned baseline imitates demonstrations generated by this controller. This is a simplification in the implementation, not a missing experiment, but the paper should state it. We added oc_fmcs_learned, in which a learned field produces every action: 45.8% on Reach and 4.2–8.3% stacking on Stack.

Question 2

Nothing was missed in the reproduction; 0% is what the original baseline configuration gives. Its noise schedule, denoising target and execution scheme were set up for a different regime, and with 16 denoising steps and a small MLP they combine into near-random actions. With the baseline upgraded to current practice, Reach goes from 0% to 62.5%, Lift from 0% to 83.3%, and Stack reaches 4.2–8.3% with 24 demonstrations and 41.7–50.0% with 192.

Also updated

Stack now uses 9 phases to match its 9 controller states; the Lift script runs under recent Isaac Lab releases; the Stack command in the READMEs uses the flag names the script accepts.

Question 1

The 3D oc_fmcs is a scripted controller

What the code does

In the evaluation loop of experiments/isaaclab_multitask_policy_baselines.py, the oc_fmcs branch is a single line:

elif method == "oc_fmcs":
    action = controller.action(obs)

controller is a ScenarioController (PhaseFeedbackController in the Lift script). In each state it emits a fixed end-effector target and gripper command. Once the end effector is close enough to the target (0.12 m in the configuration used here, --stack-overlap-threshold) and has dwelt long enough, it moves to the next state. Isaac Lab's differential IK tracks the target, and no network is called. The nine Stack states are:

  1. 0StartHold current posegripper open
  2. 1ApproachAbove cube 2gripper open
  3. 2DescendCube 2 grasp posegripper open
  4. 3CloseCube 2 grasp posegripper closed
  5. 4Lift0.26 m above cube 2's startgripper closed
  6. 5TransferAbove cube 1gripper closed
  7. 6Place0.095 m above cube 1gripper closed
  8. 7Release0.095 m above cube 1gripper open
  9. 8RetreatRetreat posegripper open

The demonstrations used to train BC, chunk MLP, DDPM and their phase-conditioned variants are all generated by this state machine. Table VI therefore compares learned policies that imitate the state machine against the state machine itself.

How this relates to the paper

In Algorithm 2 the local transport inside each chart comes from a learned vθ(x, t, k). The robot experiments replace that layer with the analytic field toward the current chart's target: once the target z is known, the conditional field ut(x | z) = ct(z − x) gives the direction directly, and IK executes it. The chart partition and the overlap gating (the atlas) are used as described; the local field is not learned. The text does not state this simplification, and readers and reviewers are likely to ask the same question.

What happens with a learned field

To answer that, we added the method oc_fmcs_learned. The state machine only supplies the current chart k and the handoff times. Its own action is discarded, and every executed action comes from the learned field:

  • The field acts on 16-step action chunks (16 × 8 = 128 dimensions on Stack), conditioned on the observation and a one-hot encoding of chart k.
  • Each chart's convex feasible set is the bounding box of that chart's demonstration chunks in normalized space, padded by 0.1 in every dimension. The prior is a standard Gaussian clipped to this box, which is the paper's projected prior.
  • The network predicts the endpoint ẑ, and the velocity is v = (ẑ − x) / (1 − t), the paper's conditional field ct(z − x). ẑ is clipped to the box, so every Euler step is a convex combination of x and ẑ and the iterate never leaves the chart. Integration uses 10 steps.

The learned field lifts the cube but rarely completes the stack. The chart below counts the time spent in each controller state while evaluating Stack with 24 demonstrations, out of 24 environments × 240 steps. The state machine spends 4.6% of the time in the lift state. oc_fmcs_learned and phase-DDPM both spend about 68% of it there.

The gate explains this. Leaving the lift state requires the end effector to come within 0.12 m of a scripted waypoint 0.26 m above cube 2's starting position. The learned policy lifts the cube but does not reach that particular point, so the handoff never fires. The lift state is short in the demonstrations (about 5% of steps), so there is little training data for it. DDPM without phase conditioning never passes through this gate, which is why with 192 demonstrations it stacks more often (41.7–50.0%) than any phase-conditioned method.

To report a learned OC-FMCS in the paper, the handoff should test object state, for example the cube's height above the table and its horizontal distance to the target, instead of the end effector's distance to a scripted waypoint.

Question 2

Why Diffusion stayed at 0%

Nothing was missed in the reproduction. The 0% comes from the original baseline configuration, where three settings combine.

1. A 16-step schedule that never reaches pure noise

The original configuration uses the linear schedule from the DDPM paper, βt = linspace(1e-4, 0.02), which was designed for 1,000 steps, with only 16 steps. The cumulative coefficient at the last step is:

ᾱT = ∏t=1..16 (1 − βt) = 0.851,  √ᾱT = 0.922

The noisiest input seen in training still carries about 92% signal, while sampling starts from pure Gaussian noise N(0, I), so the first denoising step is already out of distribution. The upgraded baseline uses the cosine schedule (squaredcos_cap_v2), which reaches ᾱT ≈ 1×10−5 in 16 steps.

The schedule alone is not enough. Changing only the schedule on Stack (row B of the ablation below) still gives 0%.

2. ε-prediction does not train at this network size

The original network predicts the noise ε. Action chunks have 112 (Reach) or 128 (Stack) dimensions and the network is a width-256 MLP, which struggles to reproduce a high-dimensional Gaussian sample exactly. Clean action chunks lie on the low-dimensional structure of the demonstrations, so predicting them directly (x₀-prediction) is much easier. To separate the generator from closed-loop effects we ran an offline diagnosis: without the simulator, on expert states from the evaluation seed, we compare each method's first action with the expert's.

After 6,000 training steps ε-prediction still has 8.3 cm of error on Reach. On Stack its error is 12.2 cm and the gripper direction is wrong 27% of the time, against 3.1 cm and 2.7% for x₀-prediction. Flow matching behaves the same way: 14–15 cm when predicting velocity and 3–4 cm when predicting the endpoint. This agrees with Li and He (2025), Back to Basics: Let Denoising Generative Models Denoise, who observe that with limited capacity, predicting clean data is far more stable than predicting noise or velocity.

3. Execution and sampling details

The original configuration samples a new chunk at every control step and executes only its first action. The upgraded baseline follows Diffusion Policy: it executes the first 8 actions of a chunk before resampling, and resamples immediately when the phase changes. It also adds standard practice: x₀ clipped to the demonstration range, posterior variance β̃, and an exponential moving average of the weights (0.995).

The jitter seen in simulation comes mainly from settings 1 and 2: the denoiser outputs near-random actions and the gripper command flips back and forth. The table below gives jitter metrics on Stack with 24 demonstrations. With the schedule and execution already upgraded but ε-prediction kept (row C), the gripper flips 83 times per episode. With x₀-prediction this drops to 2.5, on par with the chunk MLP and the state machine.

Paper

Implications for the paper

  • The two DDPM rows of Table VI should use the upgraded baseline. At the paper's data size (24 demonstrations) the upgraded DDPM scores 4.2–8.3%, so its ranking against OC-FMCS does not change.
  • With 192 demonstrations, DDPM without an atlas stacks in 41.7–50.0% of episodes, close to the state machine's 62.5–66.7%. Statements that a global prior cannot supply contact topology need a data-size qualifier or a rewrite.
  • The robot section should state that OC-FMCS is implemented as the atlas plus an analytic local field executed by IK. Claiming a learned local field requires results such as oc_fmcs_learned, together with a description of the gate.
  • Robot results should report the mean and range over several runs. With 24 environments, a difference of one or two environments is within noise.

Reproduction

Run from the repository root. main produces the main results and ablation the ablation. Each run is a separate Isaac process using about 2 GB of GPU memory.

export ISAACLAB_PYTHON=<isaac-lab-python>
bash docs/isaac_ddpm_fix/run_isaac_ddpm_fix.sh main
bash docs/isaac_ddpm_fix/run_isaac_ddpm_fix.sh ablation

A single Stack run:

"$ISAACLAB_PYTHON" experiments/isaaclab_multitask_policy_baselines.py \
  --scenario stack --num-envs 24 --steps 240 --hidden-dim 256 \
  --diffusion-train-steps 1800 --fm-train-steps 1800 \
  --stack-overlap-threshold 0.12 --stack-lift-z 0.26 --stack-place-z 0.095 \
  --stack-close-dwell 1.2 --stack-place-dwell 1.2 --stack-release-dwell 1.6 \
  --eval-methods diffusion_policy,phase_diffusion_policy,oc_fmcs,oc_fmcs_learned \
  --device cuda:0 --headless --out results/my_run/metrics.json

Offline diagnosis: export demonstrations first, then run the diagnosis in any Python environment with PyTorch.

"$ISAACLAB_PYTHON" experiments/isaaclab_multitask_policy_baselines.py \
  --scenario reach --steps 120 --num-envs 24 --demo-episodes 8 \
  --dump-demos dumps/reach_e8.pt --device cuda:0 --headless
python experiments/offline_policy_diag.py dumps/reach_e8.pt --episodes 1 8

If Stack hangs after a “module compiled using NumPy 1.x” warning, pinocchio was built against NumPy 1.x while the environment has NumPy 2.x. Add --stub-dex-retargeting (EXTRA=--stub-dex-retargeting for the rerun script). It only replaces teleoperation modules that evaluation never uses.

Result folders in docs/isaac_ddpm_fix/results/ map to the runs above: A = *_legacy, B = stack_24demos_cosine_only, C = *_cosine_eps, D = stack_24demos_cosine_eps_6000steps, E = stack_24demos_fixed_noclamp, E′ = stack_24demos_fixed. In the noclamp runs DDPM already uses the upgraded configuration and only oc_fmcs_learned lacks endpoint clipping. In the ablation folders oc_fmcs_learned is an earlier velocity-predicting version; use the *_fixed folders for it.
