FMCS 机器人实验复查

复现论文 VI-D 节机械臂实验时提出了两个问题。一是三维实验里的 oc_fmcs 分支调用的是手写的阶段控制器，而不是学到的流匹配速度场。二是 Diffusion 基线的成功率一直是 0，仿真里机械臂持续抖动，碰不到目标。这一页逐个回答，并给出升级后基线的代码和结果。

分支 isaac-ddpm-fix 仿真 Isaac Lab 2.3.2，Franka IK-Abs 任务 评估种子 2027 English

结论

问题一

观察是对的。机器人实验里的 oc_fmcs 是手写的有限状态机加 IK，没有学习的速度场，所有学习型基线模仿的也是它生成的演示。这是实现上的简化，不是漏了实验，但论文正文需要写明。我们补了一个动作完全由学习的场给出的版本 oc_fmcs_learned：Reach 45.8%，Stack 叠放 4.2–8.3%。

问题二

复现没有遗漏设置，0% 就是基线原配置下的结果。原配置的噪声调度、去噪目标和执行方式面向的是另一种设定，在 16 步去噪、小 MLP 的条件下叠加，去噪器输出接近随机动作。按现在的常用做法升级基线后，Reach 从 0% 到 62.5%，Lift 从 0% 到 83.3%，Stack 在 24 条演示下为 4.2–8.3%，192 条演示下为 41.7–50.0%。

其他更新

Stack 的 phase 数调整为 9，与控制器的 9 个状态一致；Lift 脚本适配了新版 Isaac Lab；README 中 Stack 命令改用脚本接受的参数名。

问题一

三维实验里的 oc_fmcs 是手写控制器

代码里实际做了什么

在 experiments/isaaclab_multitask_policy_baselines.py 的评估循环里，oc_fmcs 分支只有一行：

elif method == "oc_fmcs":
    action = controller.action(obs)

controller 是 ScenarioController，Lift 脚本里对应的是 PhaseFeedbackController。它按当前状态给出写死的末端目标点和夹爪开合。末端离目标点足够近（本次运行的配置是 0.12 m，即 --stack-overlap-threshold）并且在该状态停留够时间后，切到下一个状态。目标点由 Isaac Lab 的差分 IK 跟踪。整个过程不调用任何网络。Stack 任务的 9 个状态如下：

  1. 0起始保持当前位姿夹爪张开
  2. 1接近cube2 正上方夹爪张开
  3. 2下探cube2 抓取位夹爪张开
  4. 3合爪cube2 抓取位夹爪闭合
  5. 4抬升cube2 初始位置上方 0.26 m夹爪闭合
  6. 5搬运cube1 正上方夹爪闭合
  7. 6放置cube1 上方 0.095 m夹爪闭合
  8. 7松爪cube1 上方 0.095 m夹爪张开
  9. 8撤离撤离位夹爪张开

BC、chunk MLP、DDPM 以及它们的 phase 条件化版本，训练用的演示也全部由这个状态机生成。所以表 VI 比较的其实是“模仿状态机的学习策略”和“状态机本身”。

和论文的关系

论文 Algorithm 2 中，每个 chart 内的局部输运由学到的 vθ(x, t, k) 给出。机器人实验把这一层换成了朝当前 chart 目标点的解析场：目标 z 已知时，条件场 ut(x | z) = ct(z − x) 直接给出方向，再由 IK 执行。chart 的划分和重叠门控（atlas）是真实在用的，局部场则不是学出来的。这是实现上的简化，正文没有交代，读者和审稿人都会有同样的疑问。

换成学习的场会怎样

为此我们新增了方法 oc_fmcs_learned。状态机只负责给出当前 chart k 和交接时机，它算出的动作被丢弃，执行的动作全部来自学习的场：

  • 建模对象是 16 步的动作块（Stack 为 16 × 8 = 128 维），网络输入为观测和 chart k 的 one-hot。
  • 每个 chart 的凸可行集取该 chart 演示动作块在归一化空间里的包围盒，各维外扩 0.1。先验是标准高斯裁剪到这个盒内，对应论文的投影先验。
  • 网络预测终点 ẑ，速度取 v = (ẑ − x) / (1 − t)，即论文的条件场 ct(z − x)。ẑ 先裁剪到盒内，于是每个 Euler 步都是 x 与 ẑ 的凸组合，迭代始终留在 chart 内。积分 10 步。

学习的场能把方块抬起来，但很少完成叠放。下图统计了 Stack（24 条演示）评估中各状态的停留时间，总量为 24 个环境 × 240 步。状态机在抬升状态只停留 4.6% 的时间，oc_fmcs_learned 和 phase-DDPM 都有约 68% 的时间停在这里。

原因在门控条件。离开抬升状态要求末端到脚本航点（cube2 初始位置正上方 0.26 m）的距离小于 0.12 m。学到的策略把方块抬了起来，却没有到达这个具体位置，交接条件一直满足不了。抬升状态在演示里本来就短（约占 5% 的步数），这一段的训练数据很少。不带 phase 的 DDPM 不经过这个门控，所以 192 条演示时它的叠放率（41.7–50.0%）反而高于所有 phase 条件化的方法。

如果要在论文里报告学习版 OC-FMCS，交接条件应改为基于物体状态的判断（例如方块离桌面的高度、方块与目标的水平距离），而不是末端到脚本航点的距离。

问题二

Diffusion 为什么一直是 0%

复现没有遗漏设置。0% 来自基线的原配置，下面三处设置叠加起作用。

一、16 步的噪声调度没有走到纯噪声

原配置用的是 DDPM 原论文为 1000 步设计的线性调度 βt = linspace(1e-4, 0.02)，但只取了 16 步。最后一步的累计系数是：

ᾱT = ∏t=1..16 (1 − βt) = 0.851， √ᾱT = 0.922

训练时模型见过的最“噪”的输入里仍有约 92% 是信号，而采样从纯高斯 N(0, I) 出发，第一步就落在训练分布之外。升级后的基线改用余弦调度（squaredcos_cap_v2），16 步下 ᾱT ≈ 1×10−5。

只修调度不够。Stack 上单独换成余弦调度（下方消融表的 B 行）仍是 0%。

二、ε-预测在这个网络规模下学不动

原配置让网络预测噪声 ε。动作块是 112 维（Reach）或 128 维（Stack），网络是宽 256 的 MLP，要把一个高维高斯噪声原样复现出来很难。干净的动作块落在演示数据的低维结构上，直接预测它（x₀-预测）容易得多。为了把生成器本身和闭环效应分开，我们做了离线诊断：不开仿真，在评估种子的专家状态上比较第一步动作与专家动作的位置误差。

训练到 6000 步，ε-预测在 Reach 上仍有 8.3 cm 的误差。Stack 上 ε-预测的误差为 12.2 cm，夹爪开合方向有 27% 是错的；x₀-预测分别为 3.1 cm 和 2.7%。流匹配也是一样：预测速度时误差 14–15 cm，预测终点时 3–4 cm。这和 Li 与 He 在 2025 年的 Back to Basics: Let Denoising Generative Models Denoise 中的观察一致：网络容量有限时，预测干净数据比预测噪声或速度稳定得多。

三、执行方式与采样细节

原配置每个控制步都重新采样一个动作块，只执行其中第 1 个动作。升级后改用 Diffusion Policy 的做法：执行动作块的前 8 步再重新采样，phase 变化时立即重新采样。同时补上了几项常规做法：x₀ 裁剪到演示范围、后验方差用 β̃、权重 EMA（0.995）。

仿真里看到的持续抖动，主要来自第一、二两处设置：去噪器的输出接近随机，夹爪信号来回翻转。下表是 Stack（24 条演示）上的抖动指标。调度和执行方式都已升级、但仍用 ε-预测时（C 行），每回合夹爪翻转 83 次；换成 x₀-预测后降到 2.5 次，和 chunk MLP、状态机相当。

论文

对论文的影响

  • 表 VI 的两行 DDPM 建议换成升级后基线的结果。在论文的数据量（24 条演示）下，升级后的 DDPM 为 4.2–8.3%，和 OC-FMCS 的排序不变。
  • 演示增加到 192 条时，不带 atlas 的 DDPM 叠放率达到 41.7–50.0%，接近状态机的 62.5–66.7%。“全局先验无法提供接触拓扑”一类的表述需要加上数据量的前提，或者改写。
  • 机器人部分应写明 OC-FMCS 的实现方式是 atlas 加解析局部场，再由 IK 执行。如果要宣称局部场是学出来的，需要报告 oc_fmcs_learned 这类结果，并说明门控条件。
  • 机器人结果建议报告多次运行的均值和范围。24 个环境下，相差一两个环境的结果都在噪声以内。

复现

在仓库根目录运行。main 跑上面的主结果，ablation 跑消融；每个运行是一个独立的 Isaac 进程，显存约 2 GB。

export ISAACLAB_PYTHON=<isaac-lab-python>
bash docs/isaac_ddpm_fix/run_isaac_ddpm_fix.sh main
bash docs/isaac_ddpm_fix/run_isaac_ddpm_fix.sh ablation

单独跑一次 Stack：

"$ISAACLAB_PYTHON" experiments/isaaclab_multitask_policy_baselines.py \
  --scenario stack --num-envs 24 --steps 240 --hidden-dim 256 \
  --diffusion-train-steps 1800 --fm-train-steps 1800 \
  --stack-overlap-threshold 0.12 --stack-lift-z 0.26 --stack-place-z 0.095 \
  --stack-close-dwell 1.2 --stack-place-dwell 1.2 --stack-release-dwell 1.6 \
  --eval-methods diffusion_policy,phase_diffusion_policy,oc_fmcs,oc_fmcs_learned \
  --device cuda:0 --headless --out results/my_run/metrics.json

离线诊断：先导出演示，再在普通 Python 环境里运行。

"$ISAACLAB_PYTHON" experiments/isaaclab_multitask_policy_baselines.py \
  --scenario reach --steps 120 --num-envs 24 --demo-episodes 8 \
  --dump-demos dumps/reach_e8.pt --device cuda:0 --headless
python experiments/offline_policy_diag.py dumps/reach_e8.pt --episodes 1 8

如果 Stack 在 “module compiled using NumPy 1.x” 警告之后卡住不动，是 pinocchio 按 NumPy 1.x 编译、环境里却是 NumPy 2.x。加上 --stub-dex-retargeting（复现脚本里用 EXTRA=--stub-dex-retargeting）即可，这个开关只替换评估中用不到的遥操作模块。

结果目录 docs/isaac_ddpm_fix/results/ 中的名称与正文对应：A = *_legacy，B = stack_24demos_cosine_only，C = *_cosine_eps，D = stack_24demos_cosine_eps_6000steps，E = stack_24demos_fixed_noclamp，E′ = stack_24demos_fixed。带 noclamp 的运行中 DDPM 配置与升级后相同，只是 oc_fmcs_learned 还没有终点裁剪；消融目录里的 oc_fmcs_learned 是早期的速度预测版本，以 *_fixed 为准。
